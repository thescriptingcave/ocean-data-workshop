# Workshop Intro — `beginners/`

**Built.** Five notebooks, ~40 minutes, five dependencies. Verified in a fresh venv
holding only `beginners/requirements.txt`: 5/5 clean, every code cell producing output,
and none of `psycopg`/`xarray`/`gsw` present.

Generated by `scripts/build_beginners.py`, which is **self-contained by design** — it
imports nothing from the rest of the repository so the CI isolation check holds.

## Dependencies

```
requests      fetching a URL        <- the course
pandas        getting it into a table
duckdb        the same thing in one line
matplotlib    plotting
jupyterlab    to read the notebooks
```

`nbclient`/`nbformat` are needed by the *builder* to execute notebooks, are installed
in CI explicitly, and are correctly absent from `requirements.txt`: a reader opens the
`.ipynb` files in Jupyter Lab and never runs the builder.

## The shape of the course

Four techniques, applied three times, so the second and third shapes are recognisable
rather than new:

| technique | role |
|---|---|
| `curl` | see the bytes yourself, before trusting anything |
| `requests` | the same fetch in Python, with a status code to check |
| `pandas` | a DataFrame, once you know the shape you were handed |
| `duckdb` | the same thing in one line, when you would rather not think about framing |

The three *shapes* are the variable. The four techniques are the transferable part.

## Notebook-by-notebook

### `00_a_url_is_a_thing.ipynb` — 5 cells

The whole course in one page. A URL is a string that names something; fetching it is
request, response, done. Does the fetch by hand with `curl` first, then the identical
thing in `requests`, then names the three shapes to come.

One code cell. Deliberately: this notebook exists to make the model small.

### `01_comma_separated_text.ipynb` — 11 cells

Source: ERDDAP `jplMURSST41`, one point, one day per September 2019, ~1.3 kB.

`curl` → `requests` → `io.StringIO` → `pandas` → `duckdb` → plot. The `StringIO` line
is the trick worth remembering: `r.text` is a string and pandas wants a file-like.

**The trap:** ERDDAP sends a names row *and* a units row. Without `skiprows=[1]` every
row shifts by one, the first data value is the string `"UTC"`, and nothing raises.

**The subtlety worth keeping:** pandas needed `skiprows`; DuckDB needed neither a skip
nor a filter to find the header, but *did* leave the units line sitting in the table as
data, which is why the arithmetic failed until you filtered and cast in SQL. Neither
tool is smarter — they guess differently and here each got half of it. That is the
real lesson, and it is more useful than a rule about which tool to use.

DuckDB needs, verbatim:

```sql
SELECT time::TIMESTAMP, analysed_sst::DOUBLE
FROM read_csv_auto('<url>')
WHERE time <> 'UTC'
ORDER BY time
```

Note `skip=1` **breaks** it — it promotes the units row to be the header.

### `02_json.ipynb` — 14 cells

Source: NOAA CO-OPS tides & currents, station 9414290, 2024-01-15 to 16, hourly.
Returns `{"metadata": {...}, "data": [{...}, ...]}`, 48 rows.

`r.json()` → inspect `type()` and `.keys()` first → `pd.json_normalize` → rename →
plot. Draws the nested shape out as ASCII, because reading the shape before acting on
it is the move to teach.

**The trap, and the real lesson of JSON:** the columns arrive as `t`, `s`, `d`, `dr`,
`g`, `f`. The data is fine; the names are hostile, and the mapping lives in the
product documentation, not in the response. There is no technique that avoids reading
the docs. The best you can do is look at `df.columns` before trusting them.

**Where DuckDB stops helping, honestly:** this response is an *object* wrapping the
list, so `read_json_auto` returns one row with two nested columns. DuckDB reads
*list-shaped* JSON in one line. Showing the object case is more useful than forcing
DuckDB into every cell.

### `03_compressed_text.ipynb` — 14 cells

Source: NDBC 46092, `46092h2019.txt.gz`, hourly, 7,835 rows, ~76 kB.

`r.text` on gzip gives a few hundred characters of mojibake and **raises nothing** —
it decodes a compressed stream as language. `r.content` + `gzip.decompress` is the
actual file. This is the shape that catches everyone once.

Then: line 0 is names, line 1 is units, data starts at line 2. Same trap as 01, and
`lstrip("#")` on the names row because NDBC prefixes them.

**The trap that loses data quietly:** sentinels. `99` means missing in most columns;
`999` means missing in `WDIR`. A blanket "`>= 99` is missing" filter is **wrong**,
because a 99-degree bearing is a real wind. That filter does not raise; it deletes
real weather. Mask per column, because the sentinel is per column.

**The honest DuckDB ending:** DuckDB *refuses* this file. It is space-*padded* —
columns separated by varying runs of spaces — so the sniffer cannot choose a delimiter
and declines rather than guessing wrong. You can force it by turning off the guess and
writing eighteen column names plus a nineteenth to absorb the padding; that works and
is longer than the four lines of pandas above it. The rule that comes out is *use
DuckDB when the file is well-behaved, fall back to pandas when it is not* — the
one-liner is only a one-liner while the guessing happens to be right.

Splits the wind into `offshore_ms` (northerly → negative) and `alongshore_ms`, because
negative offshore is the upwelling signal on this coast and it gives the reader
something to have actually computed.

### `04_now_you_do_it.ipynb` — 8 cells

Three exercises, no inline answers. Narrow the CSV to one week; move the point to San
Francisco Bay and judge whether the temperature is plausible; fetch a different CO-OPS
station and rename the columns, with the instruction to look up what `f` and `dr` mean
and say so in a comment — because that lookup is the job.

Cells are marked `YOUR TURN` and guarded by `if url:` so they run clean when executed
by the build. Closes with the four-technique table and three honest ways forward
(swap in a service you care about, add a fourth shape, add a service with an API key).

## Rules the build enforces

`scripts/build_beginners.py --execute` fails a notebook when:

- any cell raises, **or**
- any cell runs but produces no output (a silently empty fetch), exempting `YOUR TURN`

Both halves are tested. The silent-cell gate is the one worth keeping: a cell that
fetches an empty response usually means a URL changed shape upstream, and a blank cell
teaches a reader nothing.

## Things that will bite you

**Notebooks execute in a separate kernel process.** Any monkeypatch applied in the
builder — including the IPv4 fix in `references/gotchas.md` — does **not** reach the
kernel unless it is delivered on `PYTHONPATH`. This cost a failed CI run; the builder
now writes a `sitecustomize` module to a temp dir for exactly this reason.

**Do not widen the error truncation.** The builder prints 200 characters of a failure.
It was 60 once, and the cut fell one character before the part naming the reason, which
made a network fault look like an unexplained failure.
